# TypeScript Configuration for the Node.js Backend

## Context

CiteSniff uses TypeScript for both the frontend and backend, but the two applications have different runtime environments.

The frontend runs through Vite and is ultimately executed in the browser. The backend runs on Node.js and exposes the application's HTTP API through Express.

The backend therefore requires a TypeScript configuration that explicitly defines:

The JavaScript version targeted by the compiler.
The Node.js module system.
The relationship between source files and compiled files.
The Node.js type definitions available during development.
The level of type checking applied to the backend.
The files that belong to the TypeScript compilation boundary.

The initial **tsconfig.json** generated by TypeScript was reviewed rather than adopted unchanged. Some generated options were specific to more general TypeScript projects and were not appropriate for a Node.js backend, such as JSX configuration.

## Decision

Configure the CiteSniff backend TypeScript compiler specifically for Node.js using the following configuration:

```code
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "./src",
    "outDir": "./dist",
    "types": ["node"],
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "skipLibCheck": true,
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true
  },
  "include": ["src"],
  "exclude": ["node_modules", "dist"]
}
```

## Thinking Process

The configuration was derived from the backend's runtime and architectural requirements rather than from the generated TypeScript defaults.

## Node.js Runtime

**target** is set to **ES2022** because the backend targets Node.js 20 or later. This allows the compiler to target a modern JavaScript runtime without unnecessarily transforming language features that the selected Node.js versions already support.

## Node.js Modules

**module** and **moduleResolution** use **NodeNext**.

This allows TypeScript to follow Node.js's modern module-resolution behavior instead of using the browser-oriented module assumptions commonly found in frontend tooling.

## Source and Build Boundaries

The backend source code is located in:

```text
server/src/
```

Compiled output is generated in:

```text
server/dist/
```

Therefore:

```text
"rootDir": "./src",
"outDir": "./dist"
```

make the source/build boundary explicit.

Node.js Types

The backend uses Node.js APIs and therefore explicitly includes the Node.js type definitions:

```code
"types": ["node"]
```

The corresponding @types/node development dependency is installed in the backend application.

## Strict Type Checking

The backend uses:

```code
"strict": true
```

This establishes TypeScript's strict type-checking behavior as the default.

Two additional checks are intentionally preserved:

```code
"noUncheckedIndexedAccess": true,
"exactOptionalPropertyTypes": true
```

These make potentially unsafe indexed access and optional-property handling more explicit.

This supports the project's emphasis on explicit validation and maintainable, testable code.

## Module and Import Safety

The configuration also enables:

```code
"verbatimModuleSyntax": true,
"isolatedModules": true,
"noUncheckedSideEffectImports": true
```

These options make module syntax and module-level behavior more explicit during compilation.

## Compilation Boundary

Only application source code belongs to the TypeScript compilation:

```code
"include": ["src"]
```

Generated output and installed dependencies are excluded:

```code
"exclude": ["node_modules", "dist"]
```

This keeps the compiler focused on the backend source rather than generated or external files.

## Debugging and Type Information

Source maps and declaration output are enabled:

```code
"sourceMap": true,
"declaration": true,
"declarationMap": true
```

Source maps improve debugging by preserving the relationship between generated JavaScript and the original TypeScript.

Declaration files provide generated type information for the compiled backend.

## Alternatives

### Accept the Generated TypeScript Configuration by default

The initial **tsconfig.json** generated by **tsc --init** could have been used without modification.

This was not selected because the generated configuration included options that were not appropriate for this backend, including JSX configuration, while the project requires an explicit Node.js compilation boundary.

## Use a Browser-Oriented Module Configuration

A browser-oriented module configuration would be more closely associated with the frontend build environment.

It was not selected because the backend is executed by Node.js and should use Node's module-resolution behavior.

## Consequences

### Positive

The backend has an explicit Node.js TypeScript configuration.
Source and compiled output have clear boundaries.
Strict type checking is enabled.
Node.js APIs have explicit type support.
The configuration is understandable and maintainable for a small full-stack application.
The backend's runtime assumptions are visible in the repository.

## Negative

The configuration is more deliberate than the default generated by TypeScript.
NodeNext module behavior requires developers to understand Node.js module semantics when adding backend files.
Declaration and source-map files add build output that is not required by the application runtime itself.

## Follow-up

The configuration will be validated when the first backend source files are created and compiled.

Further TypeScript configuration changes should be made only when an actual backend requirement justifies them.
